# 03.3 - Dynamic Inventory & Output State Binding

## The Terraform-to-Ansible Bridge

In automated provisioning workflows, server IP addresses are unknown before Terraform provisions the underlying virtual machines. Provisioning generates dynamic IP addresses that must be bound to Ansible inventory configurations for application setup.

InfraCanvas implements **Dynamic Inventory & Output State Binding** during Phase 02 of the runner pipeline (`apps/api/runner/runner.go`).

```mermaid
flowchart TD
    TFApply[Terraform Apply Finished] --> TFOutput[Exec: terraform output -json]
    
    TFOutput --> ParseJSON[Parse Output Attributes<br/>public_ip, instance_ids]
    
    ParseJSON --> ModeCheck{Sandbox or Cloud?}
    
    ModeCheck -->|Sandbox (LocalStack)| RemapSandbox[Map to localhost:2222 / localhost:2223<br/>Use sandbox/id_rsa SSH Key]
    ModeCheck -->|Real Cloud (AWS)| RealIP[Extract EC2 Public IP<br/>Use Vault SSH Private Key]

    RemapSandbox --> WriteHosts[Write ansible/hosts.ini]
    RealIP --> WriteHosts

    WriteHosts --> RunAnsible[Exec: ansible-playbook -i hosts.ini playbook.yml]
```

## Generated `ansible/hosts.ini` Example

### Sandbox Mode (Simulated Containers):
```ini
[webservers]
server1 ansible_host=localhost ansible_port=2222 ansible_user=root ansible_ssh_private_key_file=./sandbox/id_rsa ansible_ssh_common_args='-o StrictHostKeyChecking=no'
server2 ansible_host=localhost ansible_port=2223 ansible_user=root ansible_ssh_private_key_file=./sandbox/id_rsa ansible_ssh_common_args='-o StrictHostKeyChecking=no'

[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

### Production Cloud Mode:
```ini
[webservers]
server1 ansible_host=54.210.12.84 ansible_user=ubuntu ansible_ssh_private_key_file=/tmp/run-xxx/ssh_key.pem ansible_ssh_common_args='-o StrictHostKeyChecking=no'

[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

## Generalized Reactive Parameter Hydration Engine

To extend output binding beyond simple server public IPs to arbitrary parameters (e.g. Subnet IDs to VPCs, Database Endpoints to App configurations), InfraCanvas supports reactive expression bindings:

```mermaid
flowchart TD
    TFApply[Phase 01: Terraform Apply Complete] --> OutputJSON[Exec: terraform output -json]
    OutputJSON --> HydrateEngine[HydrateDynamicParameters Scanner]
    HydrateEngine --> WalkFiles[Walk Workspace Files recursively]
    WalkFiles --> MatchRegex[Scan for expression: {{ nodes.node_name.output_key }}]
    MatchRegex --> ReplaceVal[Substitute actual resolved Terraform values]
    ReplaceVal --> WriteConfig[Write updated files back to disk]
    WriteConfig --> RunAnsible[Phase 02: Run Ansible Playbooks / K8s configs]
```

### Expression Syntax & Compilation
- **Visual Binding Expression**: `{{ nodes.node_name.output_key }}` (where dots are replaced with underscores to maintain valid HCL identifier syntax, e.g. `{{ nodes.aws_instance_web_server.public_ip }}`).
- **Terraform Output Generation**: `bundleGenerator.ts` automatically parses the canvas model parameters for these expressions and compiles corresponding outputs inside `terraform/outputs.tf` dynamically.
- **Hydration Scrubber**: The backend Go runner walks the active build directories, executing in-place substitution on `.ini`, `.yml`, `.yaml`, `.json`, and `.txt` files.
