# 05.5 - Design System & Color Palette

## Brand Identity

InfraCanvas is the single product name across every surface — landing, docs, login, dashboard, and workspace. Two legacy internal names (`OrchestrateOS`, `InfraFlow`) previously leaked into docs/login/dashboard and the workspace/export-code headers respectively; both were rebrand artifacts from earlier design passes and have been fully removed as of 2026-08-20.

The brand mark is a rounded-square gradient tile (indigo → amber) containing a 2x2 blueprint-grid SVG glyph:

Used at full size (`h-8`/`h-9` + SVG glyph) on the landing navbar and the workspace/export-code headers — the "flagship" surfaces. Login, docs, and dashboard headers use a simplified variant (a plain gradient square, no glyph) as secondary chrome; this is an intentional two-tier system, not an inconsistency.

## Color Tokens

Defined once in `apps/web/app/globals.css` under `:root`, then re-exposed as Tailwind utilities via the `@theme` block (`bg-background`, `bg-card`, `border-border`, etc.). Every screen must consume these tokens rather than raw Tailwind palette classes (`slate-900`, `slate-950`, etc.) or one-off hex values — see the Historical Bug section below for why this matters.

| Token | Hex | Role |
|---|---|---|
| `--background` | `#07080B` | Page background (near-black, indigo-tinted, NOT Tailwind's blue-tinted `slate-950`) |
| `--card` | `#0D0F16` | Panel/surface background, one step lighter than background |
| `--secondary` / `--accent` | `#12141C` | Secondary surface, one step lighter than card |
| `--input` | `#242838` | Form fields, hover states — lightest structural surface |
| `--primary` | `#6366F1` | Brand primary (Tailwind `indigo-500`) — all primary CTAs, active states, focus rings |
| `--tertiary` | `#F59E0B` | Brand secondary (Tailwind `amber-500`) — gradient partner to primary, link-mode hover glow |
| `--destructive` | `#EF4444` | Error/delete actions (red) — was previously wrongly mapped to amber, which collided with the brand accent |
| `--border` | `#1E2233` | Default border color |
| `--ring` | `#6366F1` | Focus ring, matches primary |
| `--muted-foreground` | `#94A3B8` | Secondary/neutral text (Tailwind `slate-400`) |

Lightness ramp for structural surfaces: `background < card < secondary/accent < input`. When adding new UI, pick the token one step lighter than its parent container rather than reaching for a raw `slate-*` shade.

### Button color: gradient on marketing, flat in-product (intentional)

Landing-page primary CTAs use the full `bg-gradient-to-r from-indigo-500 to-amber-600` treatment. Every in-product surface (dashboard, login, docs, workspace) uses flat `bg-primary` (solid indigo, no gradient). This is a deliberate two-tier system, not drift to fix:

- **Marketing surface** (landing) can afford visual flourish — a gradient CTA draws the eye in a page designed to be scanned once.
- **Product surface** (dashboard/workspace) favors flat, low-noise color because primary buttons appear repeatedly across a screen a user works in all day; a gradient on every button gets visually loud fast and hurts scannability.

Both tiers share the exact same hue (`indigo-500` primary, `amber` as the secondary/accent), so brand recognition holds — only the *treatment* (gradient vs. flat) differs by context. Keep this split; do not force the landing gradient into product screens or flatten the landing CTA to match the dashboard.

## Tech-Category Palette (canvas nodes & edges)

Canvas nodes are tagged with a `tech` field (`Terraform | Ansible | Kubernetes | Source | Target`) that drives the node's top ribbon color (`ReactFlowCanvasNode.tsx`), icon tint, sidebar category headers, and edge stroke color (`useCanvasStore.ts` `onConnect`). As of 2026-08-20 these are calibrated to Tailwind's 500-tier scale so every category reads as a sibling of the brand's indigo/amber, instead of arbitrary one-off hexes:

| Tech | Color | Hex | Note |
|---|---|---|---|
| Terraform | indigo-500 | `#6366F1` | = `--primary`; also used for Terraform-to-Terraform edges (previously a mismatched violet `#844FBA`) |
| Ansible | violet-500 | `#8B5CF6` | previously `#00A4FF`, an arbitrary sky-blue with no relation to the palette |
| Kubernetes | sky-500 | `#0EA5E9` | previously `#326CE5` (K8s's real brand blue, but off-scale vs. the rest of the app) |
| Source | amber-500 | `#F59E0B` | previously `#D97706` (amber-600, one shade too dark/muddy) |
| Target | teal-500 | `#14B8A6` | previously `#0D9488` (teal-600, same issue) |

Cross-tech edge gradients (`grad-tf-ansible`, `grad-ansible-k8s` in `workspace/page.tsx`) chain these as analogous-hue transitions: indigo → violet → sky.

These hex literals are duplicated across `ReactFlowCanvasNode.tsx`, `workspace/page.tsx`, `useCanvasStore.ts`, `export-code/page.tsx`, and `bundleGenerator.ts` rather than centralized, because Tailwind v4's JIT scanner requires literal `bg-[#xxxxxx]` class strings in source to generate the corresponding CSS — a shared JS constant interpolated into a class name at runtime would not be picked up by the scanner. If this list grows again, keep the 5 files in sync manually (or migrate to CSS custom properties + a static `bg-[var(--tech-ansible)]`-style class if centralization becomes worth the tradeoff).

## Historical Bug: the "blue background" regression

Multiple product screens (`/docs` heaviest, plus `/login`, `/dashboard`, and the shared workspace editor components) accumulated raw Tailwind `slate-700` through `slate-950` classes over time instead of the `--background`/`--card`/`--secondary`/`--input`/`--border` tokens. Tailwind's default `slate` scale is blue-tinted (`slate-950` = `#020617`), which reads as a visibly different, cooler background than the token system's indigo-tinted `#07080B`+ family — this is what produced the "background is blue" complaint on `/docs`. Root-caused and swept platform-wide on 2026-08-20 (~150 occurrences across docs, dashboard, login, workspace, and the shared editor modals/panels). A stray `bg-slate-955` typo in `ProjectSettingsModal.tsx` (not a real Tailwind class) was also found and fixed while sweeping — it had been silently rendering unstyled.

**Guideline going forward:** never reach for `bg-slate-*`/`border-slate-*`/`text-slate-950` on a structural surface or button — always use the `background`/`card`/`secondary`/`input`/`border`/`primary` tokens so the blue-tint regression cannot silently reappear. `text-slate-400`/`text-slate-500` for neutral body copy is fine and already the established convention.

## Typography

The landing page's hero headline uses `Geist` (`apps/web/app/fonts.ts`, `heroDisplayFont`) instead of the app-wide `Inter` stack from `globals.css`. As of 2026-08-20 `heroDisplayFont` is applied to the landing page's root wrapper (not just the `<h1>`) so all landing copy — headings and body — renders in Geist consistently; `font-mono` code/terminal blocks on the same page still correctly render in JetBrains Mono because an element's own explicit `font-family` always wins over an inherited one. The rest of the app (dashboard, workspace, docs, login) intentionally stays on the `Inter`/`JetBrains Mono` stack — Geist is a landing-only accent, not a platform-wide swap.
