# 07.2 - Technical Pitfalls & Edge Cases

## Non-Obvious Traps & Edge Cases

This document details subtle behaviors and traps across the codebase that engineers must account for before writing new features.

---

### 1. Dependency Cycles in ReactFlow Connections
- **The Pitfall**: Users can create circular connection edges on the visual canvas (e.g. Node A -> Node B -> Node A).
- **The Impact**: Standard Kahn topological sort stalls and produces empty task lists or crashes.
- **The Defense**: `apps/web/app/lib/exportYaml.ts` detects when `sortedIds.length < nodes.length`. It appends any remaining unvisited nodes in their original array index order, ensuring the generated playbook never drops nodes.

---

### 2. Secret Redaction Order in Runner Logs
- **The Pitfall**: Replacing short substrings (e.g. 1-2 character strings) in `SecretRedactor` corrupts normal log words (e.g. replacing `in` in `Creating...` -> `Cr********g...`).
- **The Defense**: `SecretRedactor` enforces `len(s) > 3` before attempting `strings.ReplaceAll()`. Secrets are sanitized and sorted by descending length before masking.

---

### 3. Docker Compose Networking vs Local Host IP
- **The Pitfall**: When running the API server directly via `go run main.go` on the host machine, LocalStack is reached at `http://localhost:4566`. When running the API inside Docker via `docker-compose.yml`, LocalStack is reached at `http://localstack:4566`.
- **The Defense**: The runner checks the `IS_DOCKER` environment variable. If `IS_DOCKER == "true"`, it replaces `localhost` with the container service name `localstack` in generated Terraform endpoint blocks.

---

### 4. Optimistic Concurrency Overwrite Clashes
- **The Pitfall**: If User A and User B have the canvas open simultaneously, User B's auto-save could overwrite User A's changes.
- **The Defense**: `canvas_states` includes an incrementing `version INTEGER`. Updates with stale versions receive HTTP `409 Conflict`, signaling the frontend to reload.

---

### 5. GitHub Private Email Setting
- **The Pitfall**: When a GitHub user has "Keep my email addresses private" enabled in their GitHub profile, `GET /user` returns `email: null`.
- **The Defense**: `oauth.go` requests the `user:email` scope and explicitly issues a secondary call to `GET https://api.github.com/user/emails` to find the verified, primary email.

---

### 6. Next.js 16 App Router Breaking Conventions
- **The Pitfall**: Next.js 16 has breaking changes compared to earlier versions (e.g. async `params` in dynamic routes, revised turbopack behavior).
- **The Defense**: Check `node_modules/next/dist/docs/` before altering App Router page layouts.

---

### 7. Go Module `go` Directive Bumps Silently Outgrowing a Pinned Dockerfile Base Image
- **The Pitfall**: `go get`ing a new dependency can silently raise a module's `go.mod` `go` directive to that dependency's own minimum (e.g. `golang.org/x/time` v0.15.0 requires `go 1.25.0`). This compiles fine locally if the machine's installed Go toolchain is new enough, but a Dockerfile pinned to an older `FROM golang:X.Y` base image then fails at `go mod download`/`go build` with a bare `exit code: 1` — Docker's build output does not surface the actual "go.mod requires go >= 1.25.0" version-mismatch message, so it looks like an unrelated network/proxy failure unless you read the raw build log.
- **Why it happens**: the official `golang` Docker images ship with `GOTOOLCHAIN=local` (no auto-download of a newer toolchain), unlike a typical local Go install where `GOTOOLCHAIN=auto` is the default.
- **The Defense**: set `GOTOOLCHAIN=auto` on the `go mod download`/`go build` steps for any module whose `go.mod` might legitimately need a newer toolchain than the pinned base image — and use the default `GOPROXY` for that step, not `GOPROXY=direct`, since `direct` only proxies module downloads, not toolchain downloads. `apps/api/Dockerfile` established this pattern first (for its `apps/cli` sub-build, which already tracks a newer Go version than `apps/api` itself); `apps/agent-gateway/Dockerfile` needed the same fix after [[08.4 - Local Sandbox Agent Rollout & Migration Plan]]'s Phase 2 rate-limiting item added `golang.org/x/time`. Check for this class of failure first whenever a Docker build of a Go module fails at `go mod download` right after a dependency was added or upgraded.

---

### 8. SQLite "database is locked" from database/sql's Default Connection Pool
- **The Pitfall**: `apps/api` opens its `modernc.org/sqlite` connection via plain `sql.Open("sqlite", dbPath)` with no `SetMaxOpenConns` and no `busy_timeout` pragma. Go's `database/sql` package pools multiple physical connections to the same file by default — but SQLite only ever allows one writer at a time, so a second connection attempting to write while another holds the lock gets an immediate `SQLITE_BUSY`/"database is locked" error instead of waiting. Surfaced concretely: the Agent Gateway's `POST /api/internal/agents/{agentId}/callback` (an `ACTIVE` status notify, see [[08.4 - Local Sandbox Agent Rollout & Migration Plan]]'s Phase 2 heartbeat item) failed with a bare HTTP 500 moments after `apps/api` booted — right when a schema migration's write transaction and the callback's `UPDATE` could race on startup. A manual retry of the exact same request succeeded, confirming it was transient lock contention, not a logic bug.
- **A second, compounding pitfall this incident exposed**: the real error was invisible on both ends. `apps/api`'s `http.Error(w, "Database error: "+err.Error(), 500)` writes only to the HTTP response — Go's `http.Error` does **not** log server-side, so `apps/api`'s own container logs showed nothing. The Gateway's `apiclient.NotifyStatus` then discarded the response body entirely, logging only `unexpected response 500`. Diagnosing this required manually replaying the exact failed request with a client that preserves the response body (see below), rather than reading either service's logs.
- **The Defense**: `apps/api/main.go` now calls `db.SetMaxOpenConns(1)` right after `sql.Open`, forcing all queries through one physical connection so Go's pool can't create the multi-connection race in the first place — the simplest correct fix for a single-process, low-concurrency SQLite-backed service like this one (not a general recommendation for a service that actually needs read concurrency). `PRAGMA busy_timeout = 5000` is set alongside it as a belt-and-suspenders guard against a lock held by something outside the pool (e.g. a manual `sqlite3` CLI session against the same file). Also fixed the observability gap: `handleAgentStatusCallback` now `log.Printf`s the real error before calling `http.Error`, and `apiclient.NotifyStatus` now reads and includes the response body (capped at 4KB) in its returned error instead of discarding it — so a future recurrence of this or any other endpoint failure is diagnosable from logs alone, without a manual replay.
- **Diagnostic technique worth keeping**: to see a discarded HTTP error body when a client only logs the status code, replay the exact request with a tool that surfaces it — in PowerShell 7+, `Invoke-RestMethod` throws on a non-2xx response, and `$_.ErrorDetails.Message` on the caught exception holds the raw response body.
