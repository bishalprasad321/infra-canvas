# 07.1 - Critical Bugs Encountered & Solutions

> [!IMPORTANT]
> **READ THIS FIRST BEFORE CODING NEW FEATURES**
> This document logs the most severe engineering hurdles and bugs encountered during InfraCanvas development, detailing their root causes and verified solutions.

---

## 1. LocalStack 3.x Missing AMIs Crash Terraform

### Symptom
Running `terraform apply` with an AWS EC2 instance (`aws_instance.web_server`) failed with:
`Error: couldn't find resource ami-0c55b159cbfafe1f0`.

### Root Cause
Older LocalStack releases (v1.x/v2.x) mocked any arbitrary string starting with `ami-` as a valid image. LocalStack 3.x changed this behavior: no AMIs are pre-seeded in the mock registry, causing Terraform's AWS provider to fail during EC2 creation.

### Solution
In `apps/api/runner/runner.go`, implemented `registerLocalStackAMI()` before running Terraform:
1. Performs an HTTP POST call to LocalStack's EC2 endpoint:
   `Action=RegisterImage&Name=infracanvas-ami&RootDeviceName=%2Fdev%2Fsda1&Version=2016-11-15`.
2. Extracts the resulting AMI ID (e.g. `ami-95847382`) via regex.
3. Automatically writes this AMI ID into the `terraform/variables.tf` override.

## 2. SQLite CGO Compilation Breakages on Windows & Docker

### Symptom
The Go backend failed to build on Windows environments and in lightweight Docker alpine containers with:
`cgo: C compiler "gcc" not found: exec: "gcc": executable file not found in %PATH%`.

### Root Cause
The standard `github.com/mattn/go-sqlite3` driver relies on CGO, requiring a full GCC/MinGW C toolchain installed on the host.

### Solution
Switched the SQLite driver to **`modernc.org/sqlite`**.
- Pure Go port of SQLite generated via ccgo.
- Requires zero CGO dependencies (`CGO_ENABLED=0` works out of the box).
- Eliminates cross-compilation failures across Windows, macOS, and Linux containers.

## 3. APT & DPKG Lock Contention in Docker Containers

### Symptom
Ansible playbooks failed during package installation tasks with:
`E: Could not get lock /var/lib/dpkg/lock-frontend - open (11: Resource temporarily unavailable)`.

### Root Cause
Docker containers running automated background tasks (or restarted quickly) often left stale lock files or unattended upgrades holding the APT database.

### Solution
In `apps/web/app/lib/exportYaml.ts`, injected automated lock buster and IO optimization tasks into the playbook header:
1. `killall -9 apt apt-get dpkg || true`
2. `rm -f /var/lib/dpkg/lock-frontend /var/lib/dpkg/lock /var/lib/apt/lists/lock`
3. `dpkg --configure -a`
4. Set `force-unsafe-io` in `/etc/dpkg/dpkg.cfg.d/force-unsafe-io` for I/O acceleration inside Docker storage drivers.

## 4. WebSocket Race Condition for Late-Joining Clients

### Symptom
When users clicked "Deploy" and refreshed their browser or joined on a slow connection, canvas nodes remained stuck in `idle` or `pending` even though the backend was already halfway through provisioning.

### Root Cause
WebSocket messages were purely ephemeral broadcast events. Clients connecting after an event fired missed the transition completely.

### Solution
Implemented `RunTracker` in `apps/api/main.go`:
- Stores an in-memory map of `nodeStatuses: map[string]string`.
- When a new WebSocket client connects, the server acquires `tracker.Lock()` and **replays all accumulated log lines and the latest state of all active nodes** before subscribing the client to live broadcast frames.

## 5. OAuth Account-Takeover Exploit on Unverified Emails

### Symptom
Security vulnerability where an attacker registers a third-party account with a victim's email address and takes over the victim's InfraCanvas account via social login.

### Root Cause
Auto-linking any account matching the incoming email address without checking if the OAuth provider has verified ownership of that email.

### Solution
In `apps/api/oauth.go`:
- Auto-linking is strictly gated on `email_verified == true`.
- For Google, Google guarantees email verification.
- For GitHub, `/user` does not guarantee verification, so a mandatory secondary API call is made to `GET /user/emails` to find the verified primary email (`fetchGithubPrimaryEmail`).
- If no verified email is returned, auto-linking is rejected.

## 6. OAuth Token Leakage via URL Query Parameters

### Symptom
JWT session tokens were visible in browser history and server access logs when returning from OAuth callbacks.

### Root Cause
Passing `?token=eyJ...` in query parameters causes the token to be sent in HTTP headers on subsequent requests and recorded in browser history and reverse proxy logs.

### Solution
Changed the backend redirect to use **URL Hash Fragments (`#token=...`)**:
- Hash fragments are client-side only and never sent in HTTP request headers.
- The Next.js frontend reads `window.location.hash`, stores the token in Zustand, and immediately removes the hash from the address bar with `window.history.replaceState()`.

## 7. SQLite Inability to ALTER COLUMN for Nullable Password Hash

### Symptom
Adding social login required making `users.password_hash` nullable (since OAuth users have no password). SQLite threw an error:
`SQL logic error: near "ALTER": syntax error`.

### Root Cause
SQLite does not support `ALTER TABLE ... ALTER COLUMN` syntax.

### Solution
Implemented `migrateUsersPasswordHashNullable()` in `apps/api/oauth.go`:
Performs the idempotent 6-step SQLite table rebuild dance:
1. Checks `PRAGMA table_info(users)` to test if `notnull == 1`.
2. Creates temporary table `users_new` with nullable `password_hash`.
3. Copies all data: `INSERT INTO users_new SELECT ... FROM users`.
4. Drops old `users` table.
5. Renames `users_new` to `users`.
6. Re-creates indexes and foreign key references inside a single transaction.

## 8. OpenSSH Private Key Load Failure (libcrypto error)

### Symptom
Ansible provisioning runs failed with:
`Load key "/app/data/workspace/current/ansible-ssh-key-temp.pem": error in libcrypto`
`ubuntu@ubuntu_ssh_1: Permission denied (publickey,password).`

### Root Cause
Project credentials settings allowed users to upload custom SSH private keys, which the UI serialized as a JSON string (`{"private_key": "...", "ssh_user": "..."}`) to accommodate custom SSH usernames. However, the legacy backend code (unaware of this JSON packaging) wrote the raw JSON string directly to `ansible-ssh-key-temp.pem`, causing OpenSSH's cryptographic engine (`libcrypto`) to fail parsing the key.

### Solution
1. Updated `apps/api/main.go` and `apps/api/vault/vault.go` to intercept and unmarshal JSON formatted SSH payloads, deriving both `ANSIBLE_SSH_KEY_CONTENT` and `ANSIBLE_SSH_USER` correctly.
2. Introduced the `isSandbox(canvasJSON)` helper inside `apps/api/runner/runner.go` to determine if a run is a local sandbox vs. a live cloud deployment. If inside the local sandbox, it automatically overrides the configuration, bypasses writing custom keys, and forces fallback to the static pre-authorized sandbox keys (`/app/sandbox/id_rsa`).

## 9. Ansible Host Variable Concatenation & Python Interpreter Corruptions

### Symptom
Deploying configurations targeting live virtual machines failed with:
`module_stdout: "/bin/sh: line 1: /usr/bin/python3ansible_ssh_private_key_file=/app/data/workspace/current/ansible-ssh-key-temp.pem: No such file or directory"`
`module failed to execute correctly, you probably need to set the interpreter.`

### Root Cause
When the backend appends variables like `ansible_ssh_private_key_file` to the end of `ansible/hosts.ini`, it assumed the file ended with a newline. Because the template generator outputs `ansible_python_interpreter=/usr/bin/python3` without a trailing newline character, appending directly to the string concatenated the two variables on a single line, rendering the Python interpreter path invalid on the remote server.

### Solution
Modified `apps/api/runner/runner.go` to dynamically verify if `hosts.ini` has a trailing newline before appending custom SSH key file mappings and strict host checking flags:
```go
if !strings.HasSuffix(content, "\n") {
	content += "\n"
}
```

## 10. Project Settings "Save Changes" Silently Fails with "Failed to Fetch"

### Symptom
Clicking "Save Changes" in the Project Settings modal — even with no fields edited — threw a browser-side `TypeError: Failed to fetch` in `ProjectSettingsModal.tsx`'s `handleGeneralSave`, with no corresponding error (or any log line at all) on the `apps/api` server.

### Root Cause
`PATCH /api/projects/{id}` (`handleUpdateProject`) is the only `PATCH` route in the entire API, but the global `CORSWrapper` in `apps/api/main.go` — which wraps every route via `http.ListenAndServe(":"+port, CORSWrapper(mux))` — only listed `GET, POST, PUT, DELETE, OPTIONS` in its `Access-Control-Allow-Methods` header. The browser's CORS preflight `OPTIONS` request for the `PATCH` call succeeded but didn't declare `PATCH` as an allowed method, so the browser blocked the actual request client-side before it ever reached the server — the textbook signature of a missing-method CORS failure: a bare `Failed to fetch` with zero server-side trace.

### Solution
Added `PATCH` to `CORSWrapper`'s `Access-Control-Allow-Methods` list. Found via manual end-user testing during [[08.4 - Local Sandbox Agent Rollout & Migration Plan]]'s Phase 3 verification pass — a pre-existing bug, unrelated to that phase's own changes (`CORSWrapper`/`handleUpdateProject` were never touched by it), just never triggered before since a plain page load exercises no `PATCH` calls.
