# 04.3 - AES-256-GCM Credential Vault & Fingerprinting

## Encrypted Credentials Storage

InfraCanvas allows projects to store cloud provider credentials (AWS Access Keys, GCP Service Account JSON keys, and SSH Private Keys) securely in the database (`apps/api/vault/vault.go`).

To ensure confidentiality at rest, secrets are encrypted using **AES-256-GCM (Galois/Counter Mode)** authenticated symmetric encryption.

```mermaid
graph TD
    subgraph Secret Encryption [POST /api/projects/{id}/credentials]
        Plain[Plaintext Secret Data] --> MasterKey[SHA-256 derived Master Key]
        Random[12-byte Cryptographic Nonce] --> GCM[AES-256-GCM Engine]
        Plain --> GCM
        MasterKey --> GCM
        GCM --> Cipher[Ciphertext BLOB]
        GCM --> Nonce[Nonce BLOB]
        GCM --> Tag[Auth Tag BLOB]
    end

    subgraph Database Row [cloud_credentials Table]
        Cipher --> Row[encrypted_data, nonce, auth_tag, key_fingerprint]
        Nonce --> Row
        Tag --> Row
    end

    subgraph Execution Decryption [runner.go]
        Row --> DecryptEngine[AES-256-GCM Decrypt]
        DecryptEngine --> MemoryPlain[Ephemeral In-Memory Secret for Pipeline Run]
    end
```

---

## Master Key Derivation & Encryption Parameters

1. **Master Key**: Derived from `INFRACANVAS_MASTER_KEY` environment variable. If unset, it falls back to a development secret. The string is passed through `sha256.Sum256()` to generate a 32-byte AES-256 key.
2. **Nonce**: 12 bytes generated per encryption call via `crypto/rand.Reader`. Nonces are never reused.
3. **Authentication Tag**: GCM generates a 16-byte tag ensuring data integrity and preventing tampering at rest.

## Secret Masking & Key Fingerprinting (`Fingerprint()`)

The UI allows users to identify which credential is attached to a project without revealing the secret payload over the API.

The `Fingerprint` function generates safe previews:
- **AWS Credentials**: `AKIA****VTVA` (Displays first 4 and last 4 characters of Access Key ID).
- **GCP Service Account**: `gcp-sa:<project_id> (<client_email>)` (Masks private key while revealing project context).
- **SSH Private Key**: `-----BEGIN RSA PRIVATE KEY----- (RSA/PEM Key)` (Masks the key body).

## SSH Credentials JSON Serialization

To support custom SSH usernames without adding database schema migrations, SSH credentials are serialized as a JSON string:
```json
{
  "private_key": "-----BEGIN RSA PRIVATE KEY-----...",
  "ssh_user": "ubuntu"
}
```
If the decrypted payload fails to parse as JSON, the system falls back to a plain-text private key string with the default user `ubuntu`, maintaining 100% backward compatibility.

### Sandbox Fallback Protection
This fallback lives in `apps/api/runner/runner.go` (not `vault.go` — corrected from an earlier version of this note), inline in the Ansible phase of `RunPipeline`. Whenever no custom SSH key was supplied (`sshKeyFilePath == ""`), the runner falls back to the pre-baked sandbox SSH key (`/app/sandbox/id_rsa`, or `../../sandbox/id_rsa` when running outside Docker) and username `ubuntu`. As implemented, this fallback is not actually additionally gated on `isDocker`/`isSandboxRun` at that point in the function (an earlier version of this doc claimed it was) — the upstream `isSandboxRun` check only controls whether a *custom* uploaded key gets written to a temp file at all; the fallback-read block itself runs whenever `sshKeyFilePath` is empty.

As of [[08.4 - Local Sandbox Agent Rollout & Migration Plan]]'s Phase 1, there is now a third arm ahead of this fallback: a `local_agent` run (`isLocalAgentRun`, driven by a resolved `*runner.AgentContext`) uses the per-installation key uploaded during Agent pairing — decrypted via this same vault, never the shared `sandbox/id_rsa` — instead of either the custom-key path or this fallback.
